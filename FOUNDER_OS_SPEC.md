# Founder OS — архитектура и функциональность

Версия: MVP 0.1 (6 ноября 2026). Схема данных: `schemaVersion = 1`.

## 1. Принципы

1. **Все показатели вычисляются из данных.** На экранах нет статичных цифр. Если данных нет, показывается пустое состояние, а не выдуманный показатель.
2. **Демо-данные изолированы.** Они не загружаются по умолчанию, помечены `isDemo: true` и бейджем «Демо» и удаляются одной кнопкой.
3. **Модульность.** Домен, хранение, расчёты и интерфейс разделены. Новый раздел или замена хранилища не требуют переписывать существующие.
4. **Связи между сущностями.** Задачи, события, заметки и результаты ссылаются на проект через `projectId`. Карточка проекта собирает их на одном экране.
5. **Ничего не теряется.** Проекты не удаляются, а архивируются с обязательными причиной и выводами. Восстановление переносит историю закрытия в описание.

## 2. Структура кода

```
src/
├── domain/              # Модель предметной области, без React
│   ├── types.ts         #   все сущности и AppData
│   ├── constants.ts     #   справочники: статусы, приоритеты, категории, первый спринт
│   └── factories.ts     #   создание сущностей, пустое состояние, недели спринта
├── data/
│   ├── demo.ts          # демо-набор (isDemo)
│   └── storage/         # слой хранения
│       ├── types.ts     #   контракт StorageAdapter
│       ├── localStorageAdapter.ts
│       ├── migrations.ts#   приведение данных к текущей схеме, проверка импорта
│       └── index.ts     #   ← точка подключения адаптера (Supabase меняется здесь)
├── services/            # Чистые функции расчётов, покрыты тестами
│   ├── tasks.ts         #   просрочка, зависимости, циклы, срочность, прогресс проекта
│   ├── sprint.ts        #   прогресс 90-дневного спринта и недель
│   ├── metrics.ts       #   аналитика: KPI, недельная динамика, время по проектам, неактивные проекты
│   ├── planner.ts       #   Daily Time Planner
│   └── weeklyReview.ts  #   еженедельный обзор
├── store/
│   ├── useAppStore.ts   # Zustand: данные + CRUD-действия + автосохранение и синхронизация вкладок
│   └── useUiStore.ts    # Состояние интерфейса: открытый редактор, подтверждения, тема
├── components/
│   ├── ui/              # Дизайн-система (shadcn-подход): кнопки, поля, карточки, диалоги
│   └── layout/          # Каркас: боковое меню, мобильное меню, глобальный «+»
├── features/            # Блоки по доменам: редакторы, списки, канбан, Гант, планировщик, обзор
└── pages/               # 7 разделов + карточка проекта
```

**Поток данных.** Страница читает `useAppStore`, считает показатели через `services/*` и вызывает действия store. Store при изменении данных с задержкой 250 мс сохраняет снимок через `StorageAdapter`.

**Редакторы.** Любая сущность открывается через `useUi().open({ kind, id?, initial? })`, все диалоги рендерит `EditorHost`. На этом построены глобальный «+», переходы из календаря к задаче и создание задачи с предзаполненным проектом или неделей спринта.

## 3. Модель данных

| Сущность | Ключевые поля |
|---|---|
| **Task** | title, description, projectId, priority (low/medium/high/critical), status (planned/in_progress/waiting/done), createdAt, startDate, deadline, plannedMinutes, actualMinutes, sprintId, sprintWeek, dependsOn[], reminder {enabled, offsetMinutes}, completedAt |
| **Project** | name, description, goal, startDate, deadline, status (idea/active/paused/closed), color, closure {reason, lessons, closedAt} |
| **CalendarEvent** | title, description, start, end, allDay, category (meeting/conference/payment/event/focus/personal), projectId |
| **Note** | title, content, date, category (idea/note/hypothesis/observation/material), source, projectId, tags[] |
| **Achievement** | title, date, projectId, description, metricValue, metricUnit, lessons |
| **Sprint** | name, startDate, endDate, goals[] {title, target, done}, weeks[] {index, startDate, endDate, goal} |
| **DayPlan** | date, settings, blocks[] {taskId, start, end}, fixedAt |
| **WeeklyReviewSnapshot** | weekStart, completedTaskIds, plannedHours, actualHours, overdueCount, priorities, notes |
| **AppSettings** | workday {start, end, breakMinutes, breakStart}, inactivityDays, activeSprintId |

Даты без времени хранятся как `yyyy-MM-dd`, моменты времени — как ISO-строки. Все сущности имеют `id`, `createdAt`, `updatedAt` и необязательный `isDemo`.

**Инварианты store:**
- `completedAt` выставляется при переходе в «Выполнено» и снимается при выходе из него.
- Удаление задачи снимает ссылки на неё в чужих `dependsOn`.
- Цикл зависимостей нельзя создать: проверка `createsCycle`, в интерфейсе такие пункты заблокированы.

## 5. 90-дневный спринт

- Первый спринт создаётся автоматически: **9 ноября 2026 — 6 февраля 2027** включительно, 90 дней, 13 недельных этапов (последний — 1–6 февраля).
- Прогресс считается по трём осям: время, задачи спринта, цели. Если выполнение отстаёт от времени больше чем на 10 п.п., выводится предупреждение.
- У каждой недели есть своя цель. Задача привязывается к неделе через `sprintWeek`.
- Даты спринта можно изменить: недели пересчитываются, цели этапов сохраняются. Кнопка «Следующий спринт» создаёт 90 дней сразу после окончания текущего.

## 6. Daily Time Planner

`services/planner.ts → planDay({ date, settings, events, tasks, fromMinute })`:

1. Рабочее окно `start…end` минус перерыв. Перерыв ставится в `breakStart`, а если не помещается — в середину дня.
2. Вычитаются встречи из календаря (события «на весь день» не блокируют время).
3. Для сегодняшнего дня планирование идёт с текущей минуты.
4. Кандидаты — открытые задачи. Исключаются задачи со статусом «ожидает», с датой начала в будущем и с незавершёнными зависимостями.
5. Сортировка по срочности: просрочка, затем близость дедлайна, приоритет и статус «в работе».
6. Жадное размещение по свободным окнам. Задача делится на части, блоки короче 15 минут не создаются. Длительность — остаток плана (`planned − actual`), для задач без оценки — 60 минут.
7. Результат: блоки, занятость, свободное время, список «не поместилось» и исключённые задачи с причинами.

Рабочий день задаётся по умолчанию в настройках и может переопределяться для конкретной даты. План можно **зафиксировать** (`dayPlans[date]`) — это опорная точка для будущих таймера, перепланирования и учёта факта.

## 7. Еженедельный обзор

`services/weeklyReview.ts → buildWeeklyReview(data, weekStart)` собирает:
- выполненные задачи;
- часы: план, факт, встречи;
- прогресс проектов за неделю;
- просрочки на конец недели;
- кандидатов в приоритеты следующей недели.

В понедельник на главной появляется баннер со ссылкой на обзор прошлой недели. Обзор сохраняется как снимок вместе с приоритетами и заметками. Первая строка приоритетов становится фокусом следующей недели.

## 8. Хранение и переход на Supabase

Сейчас `LocalStorageAdapter` хранит весь снимок `AppData` в одном ключе. Есть миграции схемы, экспорт и импорт JSON, синхронизация вкладок через событие `storage`.

План подключения Supabase без переписывания интерфейса:
1. Таблицы по коллекциям из `data/storage/types.ts → COLLECTIONS`: `projects`, `tasks`, `events`, `notes`, `results`, `sprints`, `reviews` и `settings` (одна строка). Колонки повторяют поля типов, `dependsOn` и `tags` хранятся как `uuid[]` и `text[]`, вложенные объекты — как `jsonb`.
2. Row Level Security: `user_id = auth.uid()` на всех таблицах.
3. Реализовать `SupabaseAdapter implements StorageAdapter` и заменить адаптер в `data/storage/index.ts`. Ключи — только публичный `anon key` из переменных окружения `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Сервисные ключи в клиент не попадают.
4. Следующий шаг оптимизации — сохранять не снимок целиком, а изменённые записи (upsert по `updatedAt`).
5. Разовая миграция: импорт текущего JSON-экспорта в Supabase.

## 9. Что является заготовкой

| Функция | Состояние |
|---|---|
| Напоминания | Настройки хранятся в задаче, уведомления не отправляются (по ТЗ) |
| Таймер и учёт факта | Фактическое время вводится вручную; зафиксированный план дня — основа для таймера |
| Автоперепланирование | План пересчитывается на лету при изменениях; автоматического переноса недоделанного нет |
| Еженедельная рассылка | Обзор формируется автоматически по запросу, без отправки |
| Supabase | Архитектура и контракт готовы, адаптер не реализован |

## 10. Качество

- TypeScript в strict-режиме, сборка без ошибок.
- 18 unit-тестов: спринт и недели, просрочка, срочность, циклы зависимостей, планировщик (встречи, перерыв, деление задач, исключения), аналитика, обзор недели, миграции, инварианты store, удаление демо.
- Проверено в браузере (Chrome): все разделы в светлой и тёмной темах, мобильный экран 390 px, сквозной сценарий CRUD с перезагрузкой. Ошибок в консоли нет.
- Палитра графиков проверена на различимость при нарушениях цветового зрения и на контраст в обеих темах.

## 11. Известные ограничения

- `localStorage` ограничен примерно 5 МБ и привязан к браузеру. Резервная копия — экспорт JSON.
- Drag & drop в канбане работает мышью. На телефоне статус меняется в карточке задачи.
- Диаграмма Ганта (gantt-task-react 0.3.9) стилизуется через хэшированные CSS-классы библиотеки. При обновлении библиотеки нужно перепроверить тёмную тему.
- Формат полей даты и времени задаёт браузер по языку системы.
